# SubTrack SLI Definitions

This document formally defines the Service Level Indicators (SLIs) for the SubTrack project. SLIs are carefully chosen ratios or aggregations of raw metrics that represent the genuine user-felt experience, providing a precise standard by which we measure if the service is "working correctly."

---

## 1. Availability (Success Rate)

**What it measures:**
The proportion of HTTP requests that successfully complete without resulting in a server error (5xx), out of all requests received, measured over a rolling window.

**Why this matters to users:**
If users try to load a page, manage a subscription, or log in, and the server crashes or fails to process the request, they experience a broken product. High availability means the system consistently fulfills valid requests. 

**Exact PromQL query:**
```promql
sum(rate(subtrack_http_requests_total{status_code!~"5.."}[5m]))
/
sum(rate(subtrack_http_requests_total[5m]))
```
*(Note: We deliberately exclude 4xx client errors from counting against availability. A 401 Unauthorized or a 404 Not Found is usually the correct system response to an invalid client request, rather than a failure of the service itself. Only 5xx genuinely represents "the service failed to do its job.")*

**Data source:**
The `subtrack_http_requests_total` metric exposed by the `subtrack-backend` at its `/metrics` endpoint (built in Section B.1).

**Known limitations:**
The availability SLI currently only reflects the backend's own HTTP error responses. It would not catch a scenario where the backend returns a successful `200 OK` status but the response body contains subtly wrong data (e.g., a business-logic bug). It also does not capture errors generated at the frontend or network layer before the request reaches the backend.

---

## 2. Latency (Fast Enough Rate)

**What it measures:**
The proportion of requests that complete in under 500ms, out of all requests, measured over a rolling window.

**Why this matters to users:**
Users expect a snappy, fluid interface. Even if a request technically succeeds, if it takes 5 seconds to load their dashboard, they will perceive the service as broken or degraded. This SLI protects the "smooth as butter" user experience.

**Exact PromQL query:**
```promql
sum(rate(subtrack_http_request_duration_seconds_bucket{le="0.5"}[5m]))
/
sum(rate(subtrack_http_request_duration_seconds_count[5m]))
```
*(Note: This is a "good events / total events" style threshold-based latency SLI. Rather than tracking a raw percentile like p95 directly, we define a threshold of acceptable performance (500ms). Expressing this as a fraction enables it to compose cleanly into error-budget math in the exact same way as the Availability SLI.)*

**Data source:**
The `subtrack_http_request_duration_seconds_bucket` and `subtrack_http_request_duration_seconds_count` metrics generated by the backend's histogram instrumentation.

**Known limitations:**
This latency measurement is entirely server-side (from the time the Node.js process receives the request to the time it finishes writing the response). It does not include network transit time to the user's browser, DNS resolution time, or client-side rendering time in the React frontend. True perceived user latency is likely higher than what this SLI records.
